1 · sorry beats the level CRITICAL FIXED

Fixed in 1bc0c55 together with #2: complete now also requires a message log with no errors and no “declaration uses `sorry`” warning. Regression-tested in tests/TestRunner.lean.

On any exercise, typing sorry and pressing Run flips the STATE card to the green “Proof complete” with the ✅ complete badge — identical to a real solve. The only tell is a small warning diagnostic below. Root cause in Runner.lean:120: 

let complete := doneInfo?.isSome && goals.isEmpty   -- never looks at error/sorry diagnostics
BUG · L01 + sorry
L01 Elements after running sorry: green “Proof complete”, ✅ complete badge, warning “declaration uses `sorry`” underneath.
BASELINE · real solve
The same level solved legitimately with exact a — visually identical apart from the diagnostics card. A learner cannot tell the difference.

2 · A failing tactic also shows “Proof complete” CRITICAL FIXED

Fixed in 1bc0c55 together with #1 (the suggested fix below, as one change to the completeness check in Runner.lean). One deviation: the sorry check matches the “declaration uses `sorry`” warning prefix — Lean 4.29 quotes it with backticks, not the single quotes assumed below.

Worse than #1: a tactic that errors still turns the state green. exact b (where b doesn’t exist) shows “error 2:8 Unknown identifier `b`” and “Proof complete” on the same screen. Lean’s elaboration error recovery closes the goal with a synthetic sorry, so at done there are no goals left and the runner’s completeness check passes. Any erroring tactic “beats” the level.

BUG · error + complete simultaneously
“Unknown identifier `b`” in red, green “Proof complete” one card above it.
Suggested fix (both #1 and #2): require a clean message log in addition to an empty goal list, e.g. 
let hasErrors := messages.toList.any fun m =>
  m.severity == .error
let usesSorry := -- check sorryAx in the proof term,
                 -- or keep the sorry warning and test for it
let complete := doneInfo?.isSome
  && goals.isEmpty && !hasErrors && !usesSorry

3 · One typo permanently bricks the level HIGH FIXED

Fixed in 108e0b1 with the undo option (nothing is dropped silently): send() snapshots the source before each commit, and an Undo button in the SOURCE header pops the snapshot and re-checks. Verified in the simulator against the repro below: exact b → Undo → exact a → genuine “Proof complete”.

Every Run appends the input to the source for good — there is no undo, no reset, and no way to edit the source. After the failed exact b above, entering the correct exact a fails with “No goals to be solved” (error recovery already consumed the goal). The goal card is gone, nothing the user types can ever succeed, and the only escape is the back button — which discards all progress and returns to the home list.

BUG · stuck state
After one typo, the correct tactic errors too. No goal card, no badge, no way out.
Repro:
  1. Open any level, run exact b (or any erroring tactic)
  2. Run the correct tactic → “No goals to be solved”
Suggested fix: drop the last tactic line when its run produced errors (treat Run as try-then-commit), or add an undo/reset control. Currently send() at ExerciseView.swift:485 commits unconditionally.

4 · Bare exact leaks the hidden done sentinel MEDIUM

Tapping the exact chip and pressing Run (a very natural “what does this button do” action) appends exact with no argument. The parser then consumes the app’s hidden done sentinel as exact’s term argument, yielding “error 4:2 Unknown identifier `done`” — line 4 doesn’t exist in the displayed source, and the user never wrote done. The structured goal card also disappears, because the runner can no longer find a done tactic node to read goals from.

BUG · implementation detail leaks
Displayed source has 3 lines; the error points at line 4 and names the sentinel the UI works hard to hide (displaySource strips it at ExerciseView.swift:252).
Same family: a parse-level failure (e.g. use p, screenshot in #8) drops the goal card and instead dumps the raw “unsolved goals” error text — hypotheses and turnstile as plain monospace — into DIAGNOSTICS. Error states consistently lose the structured goal view.

5 · CONSTANTS suggests an unusable a✝ MEDIUM

The intros chip (no names) introduces hypotheses with inaccessible names like a✝. The CONSTANTS row then offers a✝ as a tappable chip — but inaccessible names cannot be referenced in Lean source, so the resulting exact a✝ fails with “Unknown identifier `a`” + “expected token”. The app’s own suggestion pipeline (constants at ExerciseView.swift:422 takes hypothesis names verbatim) manufactures a guaranteed failure, which then bricks the level per #3.

SETUP · after intros + exact
Function World L01 after intros: hypothesis a✝ : A, and CONSTANTS dutifully offers an a✝ chip.
BUG · tapping the suggestion
“Unknown identifier `a`” / “expected token”. Fix: filter hypotheses whose names contain ✝, and/or make the intros chip auto-name (intro h style).

6 · Intro documents an input method that doesn’t exist MEDIUM

The Conjunction World intro says: “Use \< and \> to type the angle brackets”, and L01’s intro offers exact ⟨p, q⟩ as an alternative solution. That abbreviation expansion is a desktop-editor (VS Code/Emacs) feature — the app’s plain TextField does no expansion and the iOS keyboard has no ⟨ ⟩, so the documented syntax is impossible to enter. Typing it verbatim fails with “unexpected token '\'” (and bricks the level per #3).

THE INSTRUCTION
Conjunction World L00 intro, final paragraph.
BUG · following it
Typing exact \<p, q\> exactly as instructed. Fix: expand \</\> (and friends) in the input field, or add ⟨ ⟩ chips, or reword the intro.

8 · Reference ⇄ chips ⇄ build mismatch LOW

The reference documents 18 tactics, several of which don’t exist in the embedded Lean build — use is confirmed “unknown tactic” (screenshot), and rcases, mathlib-style rw, and the ℕ-specific induction entry (copied from the Natural Number Game, in a game with no naturals) are equally out of place. Conversely the exercise tactic chips offer intros and refine, neither of which has a reference entry.

BUG · documented tactic is unknown
use p → “unknown tactic”. Note also the raw “unsolved goals” dump replacing the goal card (see #4), while the proof state is actually fine.
Documented but unavailable/irrelevant: use, rcases, induction (ℕ), rw (described as “less powerful than mathlib’s”).

Offered as chips but undocumented: intros, refine.

Fix: cull the reference to the tactics this build actually supports and document every chip.

9 · Goal badge always says “goal 1 of N” LOW

The badge string is hard-coded as “goal 1 of count” (ExerciseView.swift:284). After constructor splits P ∧ Q into two goals it correctly reads “goal 1 of 2”, but after solving the first goal it reads “goal 1 of 1” — to a learner that reads as “nothing happened”, when it should convey progress (e.g. “1 goal left” or “goal 2 of 2”).

Non-bug observations

ObservationDetail
Elaboration blocks the main threadrunCheck() (ExerciseView.swift:499) calls the Lean bridge synchronously on the UI thread. The isRunning disabled state is invisible (SwiftUI never re-renders mid-call) and the app simply freezes during checks — noticeable on first open and likely seconds-long on boss levels.
No progress persistenceCompleting a level isn’t recorded anywhere: the home list shows no checkmarks, there is no “next lesson” CTA after “Proof complete”, and the back chevron jumps to the home list (skipping the lesson intro). Re-entering a solved level starts from scratch.
Inconsistent completeness on failure typeElaboration-level failures (exact b) falsely report complete (#2); parse-level failures (use p) correctly don’t. Same user mistake, opposite verdicts.
Progress bar fix verifiedThe segmented progress bar off-by-one documented in segmented-progress-bar-fix.html is confirmed fixed in this build: L01 shows segment 1 soft / none solid; L02 shows 1 solid + segment 2 soft.
🐛 Bottom line: the rendering and navigation layers are in good shape, but the correctness core is unsound — both sorry and outright failing tactics are scored as “Proof complete” (Runner.lean:120), and the no-undo input model turns any mistake into a dead end. Those two fixes (completeness must check the message log; Run must be try-then-commit or undoable) would resolve findings 1–5 at the root.

✅ Update (June 12 2026): findings 1–3 are fixed. #1 and #2 in 1bc0c55 — completeness now requires an error-free, sorry-free message log, regression-tested in tests/TestRunner.lean. #3 in 108e0b1 — an Undo button backed by a source-history stack, verified in the simulator. Findings 4–9 remain open.
